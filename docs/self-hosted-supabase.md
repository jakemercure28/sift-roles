# Self-hosted Supabase on the ThinkPad

This documents how Sift's hosted database was moved off Supabase Cloud and onto a
self-hosted Supabase stack co-located with the app on the ThinkPad, and how to
operate and reproduce it.

## Why

Egress, not features. The app runs on the ThinkPad; the DB lived in AWS
us-west-2 (Supabase Cloud). Every row read crossed the internet and billed as
**Shared Pooler Egress**, which blew past the free tier (290%). The reads were
already tuned twice; the remaining cost was structural. **Co-locating the DB with
the app drives pooler egress to ~0.** Only two Supabase features were in use —
Auth (GoTrue + Google OAuth) and managed Postgres — so the whole stack is
self-hostable with near-zero app changes.

## Topology

```
ThinkPad (Cloudflare Tunnel `prospect`, id 19cdc1fd-...)
  jsa-prod (app)     --docker net-->  supabase-prod  (db/auth/kong/studio, kong @127.0.0.1:8101)
  jsa-staging (app)  --docker net-->  supabase(staging) (db/auth/kong/studio, kong @127.0.0.1:8100)

  app.siftroles.com    -> localhost:3131 (jsa-prod)
  auth.siftroles.com   -> localhost:8101 (supabase-kong-prod)   [GoTrue]
  staging.siftroles.com-> localhost:3132 (jsa-staging)
  auth-staging.siftroles.com -> localhost:8100 (supabase-kong)  [GoTrue]
```

- Prod self-host stack: `/srv/jsa/supabase-prod/docker`, compose project `supabase-prod`,
  containers `supabase-{db,auth,kong,studio}-prod`.
- Staging self-host stack: `/srv/jsa/supabase-staging/docker`, containers `supabase-{db,auth,kong,studio}`.
- Both are the official `github.com/supabase/supabase` self-host compose (sparse
  checkout of `docker/`), trimmed at runtime to `db auth kong` (+ `studio`).

## Why no app code changed: asymmetric JWTs

GoTrue v2.189 signs access tokens with **ES256** when given `GOTRUE_JWT_KEYS`
(generated by `utils/add-new-auth-keys.sh`) and publishes the public key at
`/<...>/auth/v1/.well-known/jwks.json` (Kong already routes it). The app's
verifier (`internal/auth/supabase.go`) accepts ES256/RS256 via JWKS, so it
verifies self-hosted tokens unchanged. The app just needs:

- `DATABASE_URL=postgres://postgres:<POSTGRES_PASSWORD>@<db-container>:5432/postgres?sslmode=disable`
- `SUPABASE_URL=https://auth.siftroles.com` (issuer + JWKS source)
- `SUPABASE_ANON_KEY=<SUPABASE_PUBLISHABLE_KEY>` (the `sb_publishable_...` key)

The app connects as `postgres` (matches prior behavior; tenant isolation rides on
the app's `set_config('app.user_id', ...)` + `WHERE user_id` — see
`internal/db/repository.go`).

## Reproduce / cut over a new environment

1. **Stack:** sparse-checkout `docker/` from `supabase/supabase` into
   `/srv/jsa/supabase-<env>`. `cp .env.example .env`; run
   `utils/generate-keys.sh --update-env` and `utils/add-new-auth-keys.sh --update-env`.
2. **Config `.env`:** `API_EXTERNAL_URL`/`SUPABASE_PUBLIC_URL=https://auth[-env].siftroles.com`,
   `SITE_URL=https://<app-host>`, `KONG_HTTP_PORT` (8101 prod / 8100 staging),
   `GOOGLE_ENABLED=true`, `GOOGLE_CLIENT_ID`, `GOOGLE_SECRET`. Uncomment the
   `GOTRUE_EXTERNAL_GOOGLE_*` lines in `docker-compose.yml`.
3. **Coexistence:** to run a second stack on the same box, override
   `container_name` (`-prod`) and append the override file to `COMPOSE_FILE` (see
   Gotchas). Set a distinct `COMPOSE_PROJECT_NAME` and Kong port.
4. **Bring up:** `docker compose up -d db` (wait healthy) then `... up -d auth kong`.
   Verify `curl 127.0.0.1:<kong>/auth/v1/.well-known/jwks.json` shows `ES256`.
5. **Tunnel:** add `auth[-env].siftroles.com -> localhost:<kong>` to
   `/etc/cloudflared/config.yml` (above the 404 catch-all),
   `cloudflared --config <f> tunnel ingress validate`, apply,
   `cloudflared tunnel route dns <tunnelid> auth[-env].siftroles.com`, reload cloudflared.
6. **Google:** add `https://auth[-env].siftroles.com/auth/v1/callback` to the
   OAuth client's Authorized redirect URIs. **Use the client whose id/secret the
   stack is configured with.**
7. **Migrate data** (same PG major both sides):
   ```sh
   SRC=<hosted session-pooler url, port 5432 not 6543>
   docker exec <db> pg_dump "$SRC" --schema=public --no-owner --no-privileges > public.sql
   docker exec <db> pg_dump "$SRC" --data-only --table=auth.users --table=auth.identities --column-inserts > authdata.sql
   docker exec -i <db> psql -U postgres -d postgres < public.sql
   docker exec -i <db> psql -U postgres -d postgres < authdata.sql
   ```
   `auth.identities` carries the Google `provider_id`, so re-login maps to the same
   `user_id` and tenant data stays attached.
8. **Cut over:** `docker network connect <app-net> <db-container>`; point the app
   `.env` at the local stack (3 vars above); restart with the right project name
   (`-p jsa-prod` / `-p jsa-staging`).
9. **Verify:** app `healthz` 200, app DB connections land on the local PG, real
   Google login returns your data. Keep the hosted project **paused ~2 weeks** as
   a one-command rollback (revert the 3 env vars + restart).

## Backups (the one responsibility self-hosting adds)

`/srv/jsa/backups/backup-supabase.sh` dumps public schema + auth users/identities,
tars + gzips, keeps a local copy (14d) and copies offsite to Backblaze B2 (15d)
via rclone. Daily crons:

```
10 4 * * *  ENV_LABEL=staging DB_CONTAINER=supabase-db       (offsite .../staging)
25 4 * * *  ENV_LABEL=prod    DB_CONTAINER=supabase-db-prod  (offsite .../prod)
```

Remote: `jsabackup:siftroles-db-backups` (B2, private, SSE-B2, no object-lock so
retention prune works). Restore = a fresh stack, then `psql public.sql` then
`psql authdata.sql`.

## Gotchas (learned the hard way)

- **`COMPOSE_FILE` pins the file list.** Supabase's `.env` sets
  `COMPOSE_FILE=docker-compose.yml`, which **disables auto-loading
  `docker-compose.override.yml`**. Append `:docker-compose.override.yml` to it or
  `container_name`/port overrides are silently ignored.
- **Restart app stacks with the project name** (`-p jsa-prod`/`-p jsa-staging` +
  the env's compose files). Bare `docker compose up` in `/srv/jsa/<env>` uses
  project `<env>` and spawns duplicate containers / port collisions.
- **Kong key-auth:** use the legacy `ANON_KEY`/`SERVICE_ROLE_KEY` (JWTs) as the
  `apikey` header for GoTrue admin/token calls, not the `sb_publishable_` key.
- **One OAuth client per redirect set.** `redirect_uri_mismatch` almost always
  means the callback was added to a *different* OAuth client than the one the
  stack's `GOOGLE_CLIENT_ID` points at. Check the `client_id` in
  `/auth/v1/authorize?provider=google`.
- **Stale browser/PWA cache of `/api/auth/config`** can send returning users to
  the old backend after a cutover (also surfaces as `redirect_uri_mismatch`).
  Fixed by `Cache-Control: no-store` on that endpoint; incognito is the quick
  client-side workaround.
- **pg_dump needs the session pooler** (`:5432`), not the transaction pooler
  (`:6543`).
